# prEN 40000-1-4 (Generic Security Requirements) — mapping notes

**Designation:** `prEN 40000-1-4` (Generic Security Requirements), CEN-CLC/JTC 13 WG 9,
project JT013091, version dated 2026-05-12. The `prEN` prefix is the official designation for a
European Standard at the enquiry/approval stage. It is **not yet cited in the EU Official Journal**,
so it does **not** currently grant an Article 27 presumption of conformity, and the security-objective
names can still change before final publication (targeted ~2027). Treat this mapping as provisional.

This is the horizontal harmonised standard that turns the CRA Annex I Part I essential requirements
into a catalogue of **security objectives** (`SO.*`). It builds on the EN 18031:2024 series,
augmented for the CRA. Because prEN 40000-1-4 is organised by the same essential-requirement letters
(a)-(m) that this tool already uses (2a-2m), the mapping is one-to-one.

## CRA essential requirement → security objectives

| Tool id | CRA Annex I | Security objectives (SO.*) |
|---|---|---|
| 2a | (a) Vulnerability assessment | SO.VulnerabilityManagementProcess |
| 2b | (b) Secure configuration | SO.SecureDefaultConfiguration, SO.SecureStartupConfig, SO.FactoryReset |
| 2c | (c) Security updates | SO.Updateability, SO.AutomaticUpdates, SO.UserUpdateNotification, SO.PostponeUpdates, SO.SecureUpdate |
| 2d | (d) Access control | SO.AccessControl, SO.AccessControlReport |
| 2e | (e) Confidentiality | SO.DataStoredConfidentiality, SO.DataProcessedConfidentiality, SO.DataTransmittedConfidentiality, SO.ComAuth, SO.SecureProvisioning |
| 2f | (f) Integrity | SO.DataStoredIntegrity, SO.DataProcessedIntegrity, SO.DataTransmittedIntegrity, SO.ComAuth, SO.IntegrityReport |
| 2g | (g) Data minimisation | SO.DataMinimization |
| 2h | (h) Availability | SO.IncidentRecovery, SO.IncidentResilience |
| 2i | (i) External impact protection | SO.LimitExternalImpact, SO.PreventAttackPropagation, SO.MonitorExternalImpact |
| 2j | (j) Attack surface minimisation | SO.ReduceAttackSurface |
| 2k | (k) Reduce impact of incident | SO.ReduceImpactOfIncident |
| 2l | (l) Logging and monitoring | SO.LogSecurityRelevantActivities, SO.MonitorSecurityRelevantActivities, SO.OptionDisableDataLogging, SO.OptionDisableDataMonitoring |
| 2m | (m) Data deletion | SO.SecureDataDeletion (+ SO.DataTransmittedConfidentiality, SO.DataTransmittedIntegrity for transfer) |

**Part II (vulnerability handling)** is out of scope of 40000-1-4; it is the subject of the companion
part **prEN 40000-1-3**. Article 14 (reporting) and Annex II (user information) are regulatory/process
obligations rather than product security objectives, so 40000-1-4 does not map to them.

## Where this lives in the tool

- Framework registration: `data/mapping/meta.json` → `framework_keys.EN_40000_1_4`.
- Per-requirement mapping: `data/mapping/layer2-requirements.json` → each requirement's
  `frameworks.EN_40000_1_4` block (`references` = SO ids, `how_it_helps` = summary).
- It is then selectable in the framework picker and renders in each CRA card automatically.

When the standard is published as EN 40000-1-4, revisit the `SO.*` names and add clause numbers if the final text
introduces them.
